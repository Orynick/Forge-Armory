# Audit technique — 2026-09-06

## Résumé

Audit statique complet du projet `D2 Build Analyzer` avec vérification ciblée des flux Bungie/OAuth, Manifest, recherche, loadouts, équipement et scoring.

### Corrections appliquées

1. **OAuth**
   - ajout d'un `state` anti-CSRF dans le flux OAuth ;
   - validation du `state` au callback ;
   - ajout explicite de `redirect_uri` lorsqu'il est configuré ;
   - lecture robuste des tokens stockés ;
   - verrouillage des refresh concurrents ;
   - invalidation d'un refresh en cours lors d'une déconnexion/nouvelle authentification.

2. **Comptes Bungie liés**
   - le `primaryMembershipId` de Bungie est maintenant privilégié lorsque plusieurs comptes Destiny sont liés, au lieu de dépendre arbitrairement de l'ordre du tableau retourné.

3. **Équipement**
   - les erreurs Bungie d'équipement/transfert exposent désormais `ErrorCode/ErrorStatus` ;
   - `DestinyItemNotFound (1623)` n'est plus confondu avec un transfert déjà effectué ;
   - seul `DestinyItemAlreadyInInventory (1632)` est traité comme « transfert inutile » ;
   - les boutons d'équipement utilisent maintenant `try/finally` pour ne jamais rester bloqués en état « en cours » après une erreur globale.

4. **Réponses Bungie**
   - contrôle de `ErrorCode` même lorsque HTTP répond 200 ;
   - messages d'erreur plus exploitables pour profil, inventaire, sous-classes et triomphes.

5. **Manifest**
   - validation de la réponse Manifest et du chemin de téléchargement ;
   - protection contre deux téléchargements simultanés du même Manifest ;
   - contrôle du statut HTTP du téléchargement.

6. **Recherche**
   - version explicite du format d'index pour éviter la réutilisation d'un index obsolète après modification de l'algorithme ;
   - cache persistant compact : l'index ne duplique plus le JSON complet de chaque définition ; seules les clés et le texte normalisé sont persistés.

7. **Scoring**
   - les statistiques individuelles sont maintenant bornées à `STAT_MAX` avant pondération ; un T20 ne peut donc pas être surévalué par des points bruts au-delà du plafond.

8. **Loadouts**
   - validation minimale des loadouts importés/lus avant de les exposer à l'interface ; un JSON malformé ne doit plus casser le panneau.

9. **DIM**
   - le cache du jeton DIM est associé au `membership_id` Bungie courant, évitant de réutiliser par erreur un jeton DIM d'un autre compte après changement de compte.

10. **Hygiène de distribution**
    - le fichier `.env.local` présent dans l'archive source n'est **pas** inclus dans l'archive corrigée.

## Vérifications réalisées

- résolution des imports locaux : **OK** (`scripts/verifier-imports.mjs`) ;
- compilation TypeScript avec un environnement de déclarations de test minimal : **aucune erreur de typage du code métier détectée après exclusion des faux positifs liés aux stubs JSX** ;
- `npm run build` réel : **non exécutable dans l'environnement d'audit**, car `node_modules` n'est pas présent et l'accès au registre npm n'était pas disponible ;
- présence d'un `.env.local` dans l'archive d'origine : **confirmée** ; il a été exclu de l'archive corrigée.

## Points restant à traiter

- déplacer idéalement l'OAuth et les opérations sensibles derrière un petit backend/BFF si l'application devient publique ; un token de refresh stocké dans `localStorage` reste exposé à une éventuelle XSS ;
- ajouter un `package-lock.json` pour rendre les installations reproductibles ;
- mettre en place une vraie suite de tests automatisés (Vitest par exemple) pour le scoring, l'OAuth, les loadouts et les réponses Bungie ;
- refactorer progressivement les appels Bungie vers un wrapper commun (gestion HTTP + enveloppe Bungie + retry/backoff) ;
- sortir les composants React imbriqués de `ResumeBuild` lorsqu'ils ont leur propre état, afin d'éviter des remounts inutiles ;
- revoir le flux d'équipement multi-objets pour limiter les appels séquentiels et mieux respecter les limites de débit Bungie.

## Roadmap — prochaines étapes recommandées

Cette section transforme les points restant à traiter en plan d'évolution priorisé. L'objectif est de stabiliser le cœur du Build Analyzer avant d'ajouter des fonctions plus coûteuses, puis de préparer une intégration IA sans mélanger la logique métier Bungie avec le modèle.

### Priorité 1 — Tests automatisés

**Objectif :** pouvoir modifier le projet sans réintroduire de régression.

À couvrir en premier :

- calcul du scoring et plafonds de statistiques ;
- règles de synergie des builds ;
- parsing/validation des données Bungie ;
- gestion des erreurs Bungie (`ErrorCode`, HTTP, réponses incomplètes) ;
- OAuth et gestion de session ;
- import/export des loadouts ;
- cas limites de l'équipement et des transferts.

**Résultat attendu :** une commande de test reproductible exécutée avant chaque nouvelle version.

### Priorité 2 — Équipement et appels API

**Objectif :** rendre les actions multi-objets plus rapides et plus robustes tout en limitant les appels Bungie.

Pistes :

- regrouper les opérations lorsque l'API le permet ;
- éviter les requêtes dont les données sont déjà disponibles localement ;
- mettre en place une file d'opérations avec limitation de concurrence ;
- centraliser les retries et le backoff sur les erreurs temporaires ;
- distinguer clairement les erreurs récupérables des erreurs définitives ;
- actualiser l'état de l'inventaire une seule fois après un lot d'opérations lorsque c'est possible.

**Résultat attendu :** moins d'appels inutiles, moins de risques de rate-limit et une interface qui reste réactive pendant les opérations.

### Priorité 3 — Wrapper Bungie commun

**Objectif :** supprimer la logique répétée entre les différents appels à l'API Bungie.

Le wrapper devrait idéalement prendre en charge :

1. authentification et access token ;
2. `fetch` et vérification HTTP ;
3. vérification de l'enveloppe Bungie (`ErrorCode`, `ErrorStatus`) ;
4. retry/backoff sur les erreurs temporaires ;
5. gestion centralisée des erreurs ;
6. journalisation contrôlée en développement ;
7. éventuellement cache court pour les données adaptées au cache.

Les services métier (`inventory`, `profile`, `manifest`, `loadouts`, etc.) ne devraient ensuite manipuler que des fonctions métier et ne plus répéter cette plomberie.

### Priorité 4 — Préparer l'agent IA

**Objectif :** permettre à un agent IA d'analyser un build en profondeur sans lui donner directement le contrôle de toute l'application.

#### Architecture recommandée

```text
Interface React
      │
      ├── Analyse classique locale
      │      ├── statistiques
      │      ├── perks / mods
      │      ├── fragments / aspects
      │      └── scoring
      │
      └── Assistant IA
              │
              ▼
        Backend / BFF IA
              │
              ├── contexte du build
              ├── règles / données Destiny 2
              ├── outils de recherche
              ├── outils d'analyse
              └── modèle IA
```

Le principe important est de **ne pas envoyer toute la base Manifest ou tout l'inventaire au modèle**. L'application doit d'abord construire un contexte structuré et compact : classe, sous-classe, armes, armures, statistiques, perks, mods, fragments/aspects, objectifs du joueur et résultats du moteur d'analyse.

L'agent pourrait ensuite disposer d'outils séparés, par exemple :

- `analyze_build` — analyse le build courant ;
- `compare_builds` — comparaison de deux configurations ;
- `search_destiny_data` — recherche dans les données Destiny 2 ;
- `explain_synergy` — explication d'une interaction entre perks/mods/aspects ;
- `find_improvements` — recherche d'améliorations possibles ;
- `check_constraints` — vérification des contraintes du build.

Le modèle **ne devrait pas être responsable des calculs déterministes**. Les calculs de statistiques, dégâts, cooldowns, coûts de mods ou règles connues doivent rester dans le moteur du Build Analyzer. L'IA doit principalement interpréter les résultats, choisir les outils pertinents, comparer les options et expliquer ses conclusions.

#### Pourquoi un backend/BFF devient intéressant

Pour un prototype local, un appel direct à un fournisseur d'IA peut suffire. Pour une application publique, un backend/BFF permettra notamment de :

- garder les clés API hors du navigateur ;
- contrôler les coûts et quotas ;
- limiter les outils accessibles à l'agent ;
- journaliser les requêtes utiles au débogage ;
- mettre en cache certaines recherches ;
- faire évoluer le fournisseur de modèle sans modifier toute l'application.

#### Ordre recommandé

1. stabiliser les tests ;
2. centraliser les appels Bungie ;
3. fiabiliser/optimiser les opérations d'équipement ;
4. créer une représentation JSON propre d'un build ;
5. créer une API backend minimale pour l'analyse IA ;
6. connecter l'agent à des outils de recherche/analyse ;
7. ajouter progressivement les fonctions conversationnelles.

**Principe directeur :** l'IA doit être une couche d'analyse au-dessus du moteur Destiny 2, et non devenir le moteur de calcul lui-même.
